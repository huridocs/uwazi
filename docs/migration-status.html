Uwazi backend · long-running migration

Migration Board

Two migrations run back to back on every part of the backend: first the module moves to the V2 hexagonal core (app/api/core), then its persistence moves from MongoDB to PostgreSQL behind a per-tenant feature flag. A module can only start the second one after it has finished the first, so the V2 column is the leading indicator and the Postgres column is the trailing one.

Track 2 — Mongo → Postgres

–

Table + DAO + mapper + data source + factory wiring behind a tenant flag, with a cross-backend consistency suite. Percentages count only areas where Postgres applies.

Next up

Ordered by what unblocks the most work, not by size. Steps 1–3 are the current front.

  1. Roll the auth flags out to tenants

    postgresUsers, postgresUsergroups, postgresCaptchas and postgresPasswordRecoveries are all built and default to off. Turning them on per tenant is what turns finished code into a finished migration.

    Blocker: user groups still has no backfill config (item 2), and the two user flags must flip together.

  2. Add the user-groups backfill config

    Every other migrated collection has a MigrateCollectionToPostgres config; user groups does not, so existing tenants' groups cannot be copied over.

    Small, well-precedented — mirror UsersMigrationConfig.

  3. Enforce the users / user-groups flag pairing

    UsersQueryServiceFactory already requires both flags before it returns the Postgres implementation, but nothing stops a tenant from being configured with only one. Today the constraint is documentation only.

    Cheap guard that prevents a confusing half-migrated tenant.

  4. Build PostgresEntitiesDataSource

    The entities table, RLS policies and backfill config exist, but only a read-side unrestricted query is wired. This is the largest remaining piece of the Postgres migration and the gate for suggestions, CSV import, relationships and sync.

    Expect the same shape as users: DAO + mapper + data source + consistency suite.

  5. Move the entity access policy to Postgres

    The permission RLS infrastructure is already in the schema; the data source is not. Doing this alongside entities keeps permission checks on one backend.

  6. Retire the legacy user-groups consumers

    collaborators.ts, entitiesPermissions.ts, search.js, activitylog/helpers.js, userGroupsMembers.ts and ServerUserGroupsService.ts still call the deprecated V1 module, so it cannot be deleted and can drift from the V2 path.

  7. Close the remaining core bridges

    Thesauri routes still run through core/v1_layer, and files keeps storage, OCR and export in V1. Both are finishing work on areas counted as migrated.

  8. Consolidate the *.v2 generation into core

    Pages, i18n, relationships, CSV and search are layered but sit outside the core and its conventions (ExecutionContext, factories, use cases). Until they move, they cannot follow the Postgres pattern.

Watch-outs

Known risks carried in the current state, not bugs to be filed.

Flag skew

Independent flags, coupled data

Users and user groups are joined in a single read. Flipping one flag without the other silently falls back to Mongo for that read path.

Three generations

Entities lives in three places

app/api/entities, entities.v2 and core all serve entity routes today. Any entity work has to account for all three.

Uneven parity

Only half the areas have a consistency suite

Files, user groups and captcha run the same assertions against both backends, and have already caught real divergences. Users, templates, thesauri, relationship types and password recoveries shipped without one — users has a spec per backend instead, which cannot catch the two drifting apart.

No TTL

Postgres has no TTL indexes

Anything relying on Mongo TTL expiry needs a scheduled cleanup job instead — captchas and password recoveries set the pattern.

Updating this page

yarn migration-status

  • The script owns the Postgres statuses; people own the prose. scripts/migrationStatus.mjs derives each area's state from the tree — schema migration, Postgres data source, tenant flag defined and wired into a factory, backfill config unless the data is ephemeral — and exits non-zero when the page disagrees with it. Run it before trusting this page.
  • It also catches new work the page has never heard of: an unclaimed Postgres*DataSource, a new postgres* flag, or a new backfill config all fail the check until an area is added to the registry and a row is added here.
  • Status lives in the row attributes. Each <tr> carries data-area, data-v2 and data-db; meters and filters compute themselves from those, so no count is ever edited by hand. Change the pill class, pill text and note to match whenever you change an attribute.
  • The V2 column is judgement, not signal — no script can tell a finished module from one that still leans on v1_layer. Re-read the code for the areas you touch.
  • Update the stamp under the title (commit, branch, review date) whenever you re-verify. The script warns when migration paths have moved since the stamped commit.
  • In Claude Code, /migration-status runs the whole loop: verify, reconcile, re-stamp, re-verify.
  • Deeper detail belongs in plans/ and issues/; keep this page to one screenful of state per area.
