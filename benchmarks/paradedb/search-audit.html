Every query pattern Uwazi runs, and what ParadeDB would do with them

A complete inventory of the Elasticsearch surface in this repo — read out of the query builders, not from memory — followed by a concrete ParadeDB schema, a pattern-by-pattern feasibility map, and the handful of things that genuinely do not port.

Three findings shape the decision more than anything else in this document.

The mapping explosion is real, and ParadeDB removes it for two of the three jobs the mapping does. The ES mapping is built by iterating every property of every template and emitting a field subtree keyed by property name, globally, across all templates — see elasticMapFactory.ts:24-70. At 3–8 leaf fields per property (16 with inheritance) against a 4,500-field ceiling, a tenant runs out somewhere around 500–900 distinct property names. ParadeDB's JSONB indexing auto-discovers every sub-path with no declared schema, which genuinely removes that ceiling for matching and filtering. It does not remove it for sorting or for per-property analysis — both still need a declaration per property, and unlike ES those declarations require a REINDEX to change. See §10 for the real shape of this. What is unambiguous is the other direction: a multi-tenant ES index makes the ceiling strictly worse, because one mapping would carry the union of every tenant's property names.

The hard part is not full-text search — it's the faceting model. Uwazi's library screen computes, in one round trip, a global-scoped aggregation per filterable property where each facet's counts re-apply every active filter except its own (metadataAggregations.js:106-120). Nested properties add a four-level nested → terms → filter → reverse_nested stack. There is no reverse_nested in ParadeDB and no nested-document model at all; this becomes N normalized-table aggregate queries, and ParadeDB's aggregate pushdown does not apply to pdb.agg() across joins. This is where the migration effort and the performance risk both concentrate.

One ES feature is load-bearing in a way that looks trivial and isn't. Page numbers in full-text snippets are recovered by injecting a [[42]] marker after every word of every PDF page (PDF.ts:35) and then stripping them at analysis time with a pattern_replace character filter. ParadeDB has no character filters. Those markers would tokenize into the index, shifting term positions and breaking phrase search on full text. Porting requires re-modelling full text as one row per page — which is a better design anyway, but it is a data-model change, not a query rewrite.

Context that changes the framing

This repo is already mid-migration from Mongo to Postgres. entities, files, templates, thesauri, users, usergroups and translations have Postgres tables, and entities already carries metadata JSONB, permissions JSONB, tenant RLS and permission-level RLS with derived _perm_read_refs / _perm_write_refs arrays (migrations 005/006/010/011). A ParadeDB index would sit on a table that already exists with roughly the right shape. That materially lowers the cost relative to a green-field port, and it means "stay on ES" also carries a cost: keeping two sources of truth in sync for the indefinite future.

§02Text search

Syntax negotiation at request time

Before every text search, Uwazi asks the cluster whether the user's string is valid Lucene syntax and picks the parser accordingly:

const validationResult = await elastic.indices.validateQuery({
  body: { query: { query_string: { query: searchTerm } } },
});
return validationResult.body.valid ? 'query_string' : 'simple_query_string';

app/api/search/search.js:726-731 — mirrored in app/api/search.v2/queryHelpers.ts:9-14

So users have the full query_string grammar available: field-scoped terms, boolean operators, phrases, wildcards, ranges, and fuzziness. The V2 client relies on this directly — the entity lookup sends title:{value}~2. When the string doesn't parse, it silently degrades instead of erroring.

Field targeting

A bare search term fans out over a computed field list: title, fullText, plus — for every unique property across every template — metadata.X.value for text/markdown/generatedid types and metadata.X.label for everything else. Non-full-text fields get boost: 2.

Full text lives in a child document

Full text is not a field on the entity. It is a separate ES document joined by { type: 'join', relations: { entity: 'fullText' } }, queried with has_child / score_mode: 'max' / inner_hits. One child per entity, id {entityId}_fullText, routed to the parent.

Per-language analysis

The child document's field name encodes its language — fullText_persian, fullText_arabic — and dynamic templates attach the matching analyzer pair. For ~30 languages the mapping defines fulltext_<lang> (index-time: lowercase, asciifolding, stemmer) and stop_<lang> (search-time: the same plus a stopword filter), with search_quote_analyzer falling back to the non-stopword variant so phrase queries still work. Arabic and Persian get normalization filters; Thai and CJK skip stemming. Language is taken from the file, or detected from the text when absent.

Other text shapes

  • Typeahead: multi_match / bool_prefix over title.sayt, title.sayt._2gram, title.sayt._3gram, and a separate 3–4 char ngram field title.sayt_ngram for mid-word matching.
  • Facet typeahead: wildcard with *term* against metadata.X.label.
  • Full-text-only groups: V2 extracts fullText:(...) groups out of the search string with a regex and routes only those to the child query.
  • Metadata-as-text filters: filterMetadataByFullText folds select filters into the scoring clause rather than the filter clause, so related entities score into results.

§03Metadata filters

Every property type has its own filter shape. Before matching, processFilters normalizes: dates go through descriptionToTimestamp (so "1 year ago" is a valid bound), text is lowercased, date/multidate/numeric collapse to range, and select values are expanded through parent thesauri so selecting a group selects its children.

The four select modes

  • any → exists on the field.
  • missing → bool.must_not.exists, OR-ed with a terms on the remaining values.
  • default → terms (OR).
  • and: true → bool.must of one term per value (AND).

Non-metadata filters

  • Template — terms on template, with a missing pseudo-value handled as must_not exists.
  • Entity ids — terms on sharedId.raw.
  • Language — term, always applied, and also pushed into the aggregation filter.
  • generatedToc — terms via the generic customFilters path.
  • Geolocation presence — bool.should of exists over every geolocation property, used by the map view. Note: no geo-distance or bounding-box queries exist anywhere in the codebase.

§04Permissions and publishing

This is the security-critical layer and the one where a migration bug is most expensive. Permissions are an array of { refId, type, level } mapped as a nested ES type, and the rules differ by role.

documentQueryBuilder.js:filterByPermissions/includeUnpublished/onlyUnpublished · search.v2/permissionsFilters.ts

This one gets easier, not harder

Postgres already enforces exactly these rules declaratively. Migration 010 derives _perm_read_refs / _perm_write_refs from the permissions JSONB via trigger, GIN-indexes them, and installs an RLS policy of published = true OR _perm_read_refs && session refIds, with a bypass flag for admin/editor/system. Under ParadeDB the permission filter stops being query-builder logic that every call site must remember to apply, and becomes an invariant the database enforces. That is a genuine correctness win — but note RLS interacts with aggregate and join pushdown, which needs measuring rather than assuming.

§05Aggregations

The most intricate part of the system, and the part that decides whether this migration is a quarter or a year.

The self-excluding facet contract

All aggregations hang off a global: {} bucket, which resets the query context to the whole index. Each facet is then a terms aggregation with a filtered sub-aggregation that re-applies the query's filters — minus the filter on its own field:

const extractFilters = (baseQuery, path) => {
  let filters = baseQuery.query.bool.filter.filter(
    match => match && (!match.terms || (match.terms && !match.terms[path])) && ...
  );
  return filters.concat(baseQuery.query.bool.must);
};

app/api/search/metadataAggregations.js:106-120

This is what makes a multi-select facet still show its unselected options with counts. Every bucket the UI reads is bucket.filtered.doc_count, never doc_count. Any replacement must reproduce it exactly or the library's filter panel silently changes behaviour.

The seven aggregation families

Template (_types)terms on template.raw, missing: 'missing', size 2000

Permissions by level / by userfilter → nested → terms → filter → reverse_nested, with the permissions filters themselves stripped from the base

Post-processing

Raw buckets are not usable output. search.js then: flattens the grouped select structure; converts nested and permission shapes into flat buckets; drops zero-count buckets; resolves keys to labels through thesauri in the request language; resolves relationship buckets to entity titles with a database round trip (getSharedIdLabelInfo); resolves permission refIds against the users and groups directories; groups children under thesaurus parents; truncates to 200 while always preserving the missing bucket; and synthesizes an any bucket from hits.total minus the missing count.

Cost profile

Each terms aggregation requests size: 2000 (PRELOAD_OPTIONS_SEARCH) and runs in global scope — i.e. across the entire tenant index, not the result set — and there is one per filterable property, plus allAggregations: true which switches it to every property. This is very likely where your current latency lives, and it is worth measuring before attributing slowness to Elasticsearch itself. A structural fix here may be available without changing datastore at all.

§07Snippets and highlighting

Highlighting uses the fast vector highlighter, which is why every searchable text field carries term_vector: 'with_positions_offsets':

highlight: {
  order: 'score', pre_tags: ['<b>'], post_tags: ['</b>'],
  encoder: 'html', type: 'fvh',
  fragment_size: 300, fragmenter: 'span',
  fields: { 'fullText_*': { number_of_fragments } }
}

Full-text highlights come back inside inner_hits on the child document; metadata highlights come back on the parent hit. The two are merged into a single { count, metadata[], fullText[] } shape.

The page-number hack

Snippets carry a page number, and this is how: when a PDF is processed, every single word in page n gets [[n]] appended to it (page.replace(/(\S+)(\s?)/g, "$1[[n]]$2")). A pattern_replace character filter named remove_annotation strips \[\[[0-9]+\]\] before tokenization, so the index is clean — but the stored text still has the markers, so the highlighter returns them and getSnippets() regexes the page number back out.

This works only because ES has character filters. ParadeDB does not. See §13.

§08Indexing and write patterns

  • Bulk index — parent entity doc plus, when the entity has a default document, a child fullText doc with routing to the parent. Page texts are joined with \f.
  • Mapping updates — putMapping runs whenever templates change; adding a property mutates the index mapping live.
  • Full reindex — delete index, recreate from getTenantESMapping(), re-emit every entity. Concurrency 10, batches of 50.
  • Deletes — by id, deleteByQuery on sharedId.raw, and deleteByQuery by language for language removal.
  • Tenancy — one index per tenant, resolved per-request from tenants.current().indexName; replica count is feature-flagged per tenant.
Already half-ported

entitiesIndex.js no longer reads entities from Mongo — it goes through EntitiesDAOFactory, and entityFiltersFromQuery translates the legacy Mongo query shapes into DAO filters, deliberately throwing on any shape it doesn't recognize rather than silently matching everything. The write path is already datastore-agnostic.

§10The mapping explosion, quantified

Worth being precise, because it drives the whole discussion.

Against index.mapping.total_fields.limit: 4500 and a base mapping of roughly 60 fields, that puts the ceiling at somewhere between 550 and 900 unique property names per tenant, depending on the type mix — and lower if nested properties are in play.

Two things make it worse than the raw number suggests

Name collisions across templates. elasticMapFactory keys on property.name globally. Two templates that both define a property called date, one as date and one as text, produce a last-write-wins mapping — silently. This is a latent correctness bug in the current design independent of any migration.

A multi-tenant index amplifies it. Merging tenants into one index means one mapping holding the union of every tenant's property names against the same 4,500 ceiling. Unless you simultaneously restructure metadata into a key-value or flattened model — which costs you per-field analysis, per-field sorting and typed range queries — the multi-tenant direction moves the wrong way on precisely the constraint you named as your main pain. Operationally it's attractive; on this specific problem it is not the fix.

What ParadeDB does instead — and where the schema comes back

Indexing a JSONB column auto-discovers every sub-path and infers each one's type. There is no per-path schema entry, so there is nothing analogous to total_fields.limit to run out of. But "schema-free" only covers part of what the ES mapping is doing for you, and the rest comes back as explicit declarations.

What the ES mapping providesUnder a plain JSONB index
Match / filter on any propertyFree, no declaration, no ceiling Direct
GROUP BY a property (facets)Supported via metadata->>'key', but the JSON field must use the literal tokenizer — which conflicts with wanting it full-text tokenized, so you need a second aliased tokenizer Rework
ORDER BY a propertyNot supported directly. "Ordering by a JSON subfield directly is not yet supported." The workaround is a declared, cast, aliased index expression per sortable path Gap
Per-property analyzerOne tokenizer for the whole column. Per-property analysis requires indexing that path as its own expression Rework
Add a property onlineFree for match/filter. Adding a sortable or specially-analyzed path means changing the index definition, which means REINDEX — where ES does an additive, online putMapping Gap

paradedb.com/docs — indexing/indexing-json, sorting/topk §"Sorting by JSON", aggregates/bucket/terms, welcome/limitations

That sorting limitation lands directly on Uwazi. sortComponets.ts:45-47 puts every text, date, numeric or select property with filter: true into the library's sort dropdown — an unbounded, user-controlled set. A pure-JSONB design would need one declared index expression per such property and a full REINDEX whenever an editor ticks the filter box on a new one. That is a worse operational story than today's live putMapping, not a better one.

Why the design in §11 is shaped the way it is

This is precisely why the proposal routes sorting and faceting through the normalized entity_metadata_values table rather than through the JSONB column. That table has fixed columns — value_text, value_num, label — so sorting and grouping by any property needs no per-property declaration and no REINDEX, no matter how many properties a tenant defines. JSONB then carries only what it is genuinely good at: matching and filtering across an open-ended property set.

So the honest version of the headline claim is narrower than "no more mapping explosion": ParadeDB removes the ceiling, but the normalized values table is what does the load-bearing work, and without it a ParadeDB migration would trade one schema-management problem for a worse one.

Three tradeoffs the docs don't cover

These follow from Tantivy, which is what actually implements the index. ParadeDB's documentation is silent on all three, so treat them as things to measure rather than facts to plan around:

  • Term dictionary cost. Tantivy encodes a JSON term as path + type marker + value, so the path string is carried inline in every term. Index size scales with distinct (path, value) pairs rather than with a compact field table. Many properties with high-cardinality values is the expensive case.
  • Type inference is per value, not per path. If metadata.date holds a number in one entity and a string in another, those become separately typed terms under the same path, and a query for one type will not see the other. Uwazi is already exposed to this: property names are global across templates today, so same-name-different-type collisions exist in the data.
  • Arrays of objects are undocumented territory. Uwazi metadata is { prop: [{ value, label, … }] }. Exactly how a JSON path under an array of objects is indexed, and whether metadata.prop.value behaves as a proper multi-valued field, is not stated anywhere in the docs. This needs a direct experiment before anyone commits to a design.

§11What a ParadeDB design looks like

Three tables, two of them new. entities already exists with the right columns.

Entities — index the existing table

CREATE INDEX entities_search ON entities USING paradedb (
  _id,
  (title::pdb.unicode_words('columnar=true')),
  (title::pdb.edge_ngram('alias=title_sayt')),   -- typeahead
  (title::pdb.literal('alias=title_sort')),      -- ORDER BY / GROUP BY
  metadata,                                      -- every property, auto-discovered
  template, language, published, "sharedId",
  "creationDate", "editDate", generatedToc,
  _perm_read_refs
) WITH (key_field = '_id');

Text and JSON fields must be columnar to be usable in ORDER BY, GROUP BY or a pushed-down join; the literal tokenizer is columnar by default. Multiple tokenizers per column via alias= is the direct analogue of ES multi-fields, and it is how title.sort, title.sayt and title coexist today.

Full text — one row per page, not per entity

CREATE TABLE entity_fulltext (
  tenant_id  TEXT NOT NULL,
  entity_id  TEXT NOT NULL,
  file_id    TEXT NOT NULL,
  page       INTEGER NOT NULL,
  language   TEXT NOT NULL,
  contents   TEXT NOT NULL,
  PRIMARY KEY (tenant_id, file_id, page)
);

This replaces the parent/child join and the [[page]] marker hack in one move: the page number becomes a column instead of an in-band annotation, and snippets come from pdb.snippets(contents) on the matching row. Per-language analysis is handled either by one aliased tokenizer per language family on contents, or by partial indexes keyed on language. Entity-level matching becomes EXISTS (SELECT 1 FROM entity_fulltext …) or a join with MAX(pdb.score(...)) for score_mode: max.

Metadata values — normalized, for faceting

CREATE TABLE entity_metadata_values (
  tenant_id   TEXT NOT NULL,
  entity_id   TEXT NOT NULL,
  property    TEXT NOT NULL,      -- 'country'
  path        TEXT NOT NULL,      -- 'value' | 'inheritedValue.value' | 'parent.value'
  value_text  TEXT,
  value_num   DOUBLE PRECISION,
  label       TEXT,
  parent_value TEXT,
  ordinal     INTEGER             -- array position: recovers nested-strict semantics
);

This is the piece that does the real work. The JSONB column alone cannot serve multi-valued facets — GROUP BY metadata->>'x' works for scalars, not for arrays of objects. A derived, trigger-maintained (or job-maintained) value table gives you: facet counts as ordinary GROUP BY, AND-mode select filters as HAVING count(*) = n, nested-strict filters via matching ordinal, and thesaurus parent/child rollups as a self-join — all with real indexes.

This is essentially the "redesign the system of record" option you raised, and the honest answer is that it is required for ParadeDB and it would also help on Elasticsearch. It is not ParadeDB-specific work.

§13The six real gaps

1. Character filters — no equivalent

The [[page]] marker scheme has no port. Feeding marked-up text to any ParadeDB tokenizer puts page-number tokens into the index between every pair of words, which shifts term positions and breaks phrase and proximity queries on full text. Mitigation: the per-page table in §11. This also removes a scheme that inflates stored full text by roughly the length of the marker per word, so it is a net improvement — but it is a data-model migration touching PDF processing, indexing, and snippet assembly.

2. Nested documents — no equivalent

Both strictNestedFilter (all conditions must hit the same array element) and the four-level nested aggregation depend on ES nested docs. Mitigation: the ordinal column. Semantically sound, but it is a full reimplementation of two of the fiddliest code paths you have, and they are covered by tests you'll want to port carefully — search.spec.js has dedicated blocks for second-level nested fields and strict-nested behaviour.

3. Facets are no longer one round trip

ES computes every facet in a single request. In ParadeDB, self-excluding counts across a normalized values table means one aggregate per facet, and pdb.agg() is explicitly not pushed down across joins — so facet queries touching entity_metadata_values fall back to native Postgres execution unless expressed as plain SQL aggregates over indexed columns. This is the largest performance unknown in the whole evaluation and the thing to prototype first. Build the values table, load one large real tenant, and measure the library screen's facet panel. Everything else is predictable; this is not.

4. Per-document analyzer selection

ES picks the analyzer from the field name, so one index serves 30 languages with correct stemming per document. ParadeDB fixes the tokenizer per indexed field. Options: one aliased tokenizer per language family on contents (index size grows with the number of families); partial indexes per language; or ICU tokenization for everything, accepting weaker stemming for stemmed languages. There is a real quality/size tradeoff here that only your corpus can settle.

5. Sorting and per-property analysis are not schema-free

ParadeDB's docs state plainly that "ordering by a JSON subfield directly is not yet supported", and that the workaround is a declared, cast, aliased index expression per sortable path. Tokenizers are likewise per indexed field, so per-property analysis also means per-property declaration. Since index columns must be defined up front and changing them requires REINDEX, a design that leans on JSONB for sorting would replace ES's additive online putMapping with a full rebuild every time an editor makes a new property filterable. Mitigation: the values table (§11), whose fixed columns make this a non-issue — which is exactly why it is not optional. Worth noting Postgres also caps index definitions at 32 columns; past that you need composite types, a beta feature.

6. Query grammar is Tantivy, not Lucene

Any saved query, public API consumer, or documented advanced-search syntax written against query_string needs re-testing. The common cases — field:term, AND/OR/NOT, phrases, ranges — carry over. Anything relying on Lucene-specific operators may not. The V2 title:x~2 lookup is the first thing to check.

Non-gaps worth striking off the list

Geospatial and vector search both show as gaps in ParadeDB's own ES comparison table, and neither applies — you run no geo queries and no vector queries. Function-score, decay functions and script scoring are also absent from ParadeDB and also unused here. Scroll and search_after are unsupported, and also unused: pagination is from/size throughout, with limit: 9999 for map and relationships views.

§14Effort shape

Rough sizing, assuming the Postgres migration continues on its current path. Treat these as relative weights, not calendar commitments.

WorkstreamWeightNotes
Metadata values table + maintenanceLargeTrigger or job, backfill, ordinal semantics, inherited & denormalized paths. Needed for facets, sorting and AND-mode filters

The counterweight is what disappears: an entire cluster to operate, version, and secure; the mapping-update-on-template-change path; the reindex-everything recovery procedure; the near-real-time refresh semantics; and the persistent class of bug where Mongo/Postgres and ES disagree. Search results become transactionally consistent with writes, which is a correctness property the current architecture cannot offer at any price.

§15How I'd frame the decision

The three options are not independent. The multi-tenant ES index, the ParadeDB move, and the "redesign the system of record" option interact:

  • Multi-tenant ES worsens the mapping ceiling unless metadata is restructured first.
  • Restructuring metadata into a normalized value table fixes faceting and sorting cost on either backend, and is a prerequisite for ParadeDB.
  • ParadeDB without the restructure does not work — JSONB alone can't serve multi-valued facets, and can't sort by a property at all without a per-property index declaration that needs a REINDEX to add.

So the metadata restructure is the common dependency, and it is the one piece of work that pays off regardless of which way the datastore decision goes. That makes it the obvious thing to do first, and doing it first also buys you a real measurement instead of an argument.

The one experiment worth running before deciding

Build entity_metadata_values against a copy of your largest real tenant, put a ParadeDB index on entities and that table, and reproduce exactly one screen: the library with its default facet panel, a text search, and a sort. Measure p50/p95 against the same query on the current ES cluster. That single comparison resolves the only genuinely unknown risk (§13.3) and de-risks the largest workstream (§14), and the table it produces is useful work either way.

What I'd expect to find

Full-text quality and latency will be fine — this workload is well within what ParadeDB is built for, and BM25 over a few million documents on one node is not exotic. The risk is concentrated entirely in faceting, and specifically in whether facet aggregates over the values table stay in the index or fall back to heap scans. If they push down, the migration is a meaningful but bounded project with a clear operational payoff. If they don't, you will need either denormalized facet-count tables or a materialized approach, and the calculus changes.

One thing to check regardless of the outcome

Every terms aggregation in the current system runs in global scope with size: 2000, once per filterable property. Before attributing library-screen latency to Elasticsearch, it's worth confirming how much of it is that. If a large share of your performance complaint is the aggregation shape rather than the engine, the same shape will be slow on ParadeDB too — and fixing it on ES is available today at a fraction of the cost.
