# Part 0 — How Uwazi search works today

## Two databases, one of them derived

Uwazi has a **system of record** (Mongo, now moving to Postgres) and a **search database**
(Elasticsearch). They hold the same entities twice.

```
  user saves an entity
          │
          ▼
  ┌───────────────┐        after commit, out of band        ┌──────────────────┐
  │  Postgres     │ ─────────────────────────────────────►  │  Elasticsearch   │
  │  entities     │            bulkIndex()                  │  one index per   │
  │  (truth)      │                                         │  tenant (copy)   │
  └───────────────┘                                         └──────────────────┘
          ▲                                                          │
          │ reads for editing                                        │ reads for the library screen
          └──────────────────────  the app  ─────────────────────────┘
```

Three consequences of that picture drive everything below:

1. **The copy can drift.** If indexing fails, the library shows entities that no longer exist, or
   misses ones that do.
2. **The copy is not immediate.** ES is _near_-real-time. A fast user can save an entity and not
   find it in the library a second later.
3. **The copy has its own schema**, and that schema is where our scaling pain lives.

## The mapping, and why it explodes

Elasticsearch needs a **mapping** — a declared list of every field in the index and its type. Ours
is generated by walking every property of every template in the tenant and emitting a small subtree
of fields per property ([elasticMapFactory.ts](../database/elastic_mapping/elasticMapFactory.ts)).

A single property is never one field. A `select` property emits eight, because it needs the label
(for display and sorting), the value (for filtering), _and the whole thing again_ under `parent` so
that thesaurus groups work:

| Property type                 | Leaf fields emitted                              | With `inherit` |
| ----------------------------- | ------------------------------------------------ | -------------- |
| text / markdown / generatedid | 3 — the object, `.value`, `.value.sort`          | 6              |
| numeric / date / multidate    | 3                                                | 6              |
| daterange / multidaterange    | 6 — `from` and `to`, each with a sort field      | 12             |
| select / multiselect          | 8 — label, value, and the whole `parent` subtree | 16             |
| relationship                  | 6                                                | 12             |
| geolocation                   | 6 — label, lat, lon                              | 12             |
| link                          | 5                                                | 10             |
| nested                        | unbounded — sub-keys mapped dynamically          | —              |

Elasticsearch enforces `index.mapping.total_fields.limit`, which we set to **4,500**
([settings.js](../database/elastic_mapping/settings.js)). With ~60 base fields, that puts the
ceiling at roughly **550–900 distinct property names per tenant**, depending on the type mix. Past
that, the collection stops working.

Two things make it worse than the number suggests:

- **Property names are global across templates.** The mapping is keyed on `property.name`, not on
  `template + name`. Two templates that both define `date` — one as a date, one as text — produce a
  silent last-write-wins mapping. This is a latent bug today, independent of any migration, and it
  comes back in a different costume under ParadeDB (§I.2).
- **A multi-tenant ES index would make it strictly worse**, since one mapping would carry the union
  of every tenant's property names against the same 4,500 ceiling.

> **This is the reason we are having this conversation at all.** Everything else in this document is
> a consequence of trying to fix it.

## Full text is not a field — it is a second document

Worth knowing before Part I, because it surprises people. The text of a PDF is not stored on the
entity document. It is a **separate ES document** linked by a parent/child join, one child per
entity, queried with `has_child` ([entitiesIndex.js:110-129](../app/api/search/entitiesIndex.js#L110-L129)).

The child's _field name encodes its language_ — `fullText_persian`, `fullText_arabic` — and ES picks
the matching analyzer (stemmer, stopwords, normalization) from that name. That is how one index
serves ~30 languages with correct linguistic handling per document.

And the page numbers in search snippets work like this: when a PDF is processed, **every single word
of page 12 gets `[[12]]` appended to it** ([PDF.ts:35](../app/api/files/PDF.ts#L35)). A character
filter strips the markers before tokenization so the index stays clean, but the _stored_ text keeps
them, so the highlighter returns them and we regex the page number back out. It is a hack, it works,
and it is load-bearing for "click a snippet, jump to the page."

## The three jobs search does

Everything the library screen asks of Elasticsearch is one of three things:

| Job               | Example                                          | Where it gets hard       |
| ----------------- | ------------------------------------------------ | ------------------------ |
| **Find text**     | "guatemala" across titles, PDFs and metadata     | Rarely — this is easy    |
| **Filter**        | template = report AND country = Guatemala        | Rarely                   |
| **Count options** | the numbers next to each checkbox in the sidebar | **This is the hard one** |

That third job deserves its own explanation, because it is the single most intricate contract in
the product and almost nobody outside the team knows it exists.

### The self-excluding facet contract

Tick "Guatemala" in the country filter. The other countries **still show their counts**, so you can
add Honduras to the selection. Meanwhile the template filter's counts _do_ drop, because they now
reflect the Guatemala selection.

That works because each filter's counts are computed with **every other active filter applied, but
not its own** ([metadataAggregations.js:106-120](../app/api/search/metadataAggregations.js#L106-L120)).

```
active filters:  template = report  AND  country = guatemala

  counts for the COUNTRY facet   → apply template=report,   NOT country
  counts for the TEMPLATE facet  → apply country=guatemala, NOT template
  counts for the AUTHOR facet    → apply both
  ...one distinct rule per filter in the sidebar
```

**Elasticsearch computes all of them in a single request**, using a `global` aggregation scope with a
filtered sub-aggregation per facet. That single-pass property is the thing a replacement has to earn
back, and it is where most of the risk in this migration sits.

Get it wrong and the failure is not "wrong numbers." The sidebar **hides any option whose count is
zero**, so ticking one option would make every other option in that filter vanish.

# Part I — Indexing

## I.1 What a ParadeDB index actually is

ParadeDB is a Postgres extension (`pg_search`) that adds a new index type. `CREATE INDEX … USING
paradedb` on the `entities` table gives you a Lucene-style search index that lives inside Postgres,
next to the B-trees, with no separate cluster.

Four properties of that index shape most of the decisions below:

**It is a covering index.** Every column you name in the index definition is _stored inside the
index_. This is deliberate — colocating the data makes reads fast — but it means the index is
roughly a second copy of whatever you index, and **all columns must be declared up front**.

**Its schema is fixed at creation.** Adding a column, removing one, or changing a tokenizer requires
rebuilding. The rebuild is online (`CREATE INDEX CONCURRENTLY` → verify → `DROP` the old one), so it
is not downtime — but it is a full pass over the corpus. Contrast with ES, where adding a mapping
field is an additive, instant `putMapping`.

**It is maintained inside the write transaction.** Rows become searchable at commit, MVCC-correct.
No refresh delay, no drift — and no out-of-band indexing either. Index maintenance moves onto the
write critical path.

**Internally it is an LSM tree of segments**, each segment holding an inverted index (term → docs)
plus a **columnar store** (values laid out per column, for sorting, grouping and aggregating).
Writes append to a small mutable segment; background compaction merges them.

That last split matters more than it sounds. Two structures, two jobs:

| Structure          | Answers                                         | Needed for                    |
| ------------------ | ----------------------------------------------- | ----------------------------- |
| Inverted index     | "which entities contain this term?"             | text search, filtering        |
| **Columnar store** | "give me this field's value for these entities" | **sorting, facets, counting** |

**Non-text columns are columnar by default. Text and JSON are not** — they need an explicit
`columnar=true` on the tokenizer, because tokenized fields can be whole documents and storing them
column-wise is expensive. Keep this in mind; it is the hinge of §I.3.

## I.2 Does it solve the mapping explosion?

**Yes — the hard ceiling genuinely disappears.** Indexing a JSONB column auto-discovers every
sub-path and infers its type. There is no per-path schema entry, so there is nothing analogous to
`total_fields.limit` to run out of. A tenant can define ten thousand properties.

### What it costs instead

| Question                       | Answer                                                                                                                                       |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **What do we pay?**            | Memory. The index lives in the Postgres buffer cache.                                                                                        |
| **Does query time grow?**      | Only for **bare text search**, which has to enumerate every property path. Linear in property count. Filtered and sorted queries don't grow. |
| **Are transactions affected?** | Yes — same buffer cache, and index writes happen inside the transaction.                                                                     |
| **Mitigation?**                | RAM, and cap the bare-search fan-out to filterable properties instead of all of them.                                                        |
| **Scaling?**                   | Vertically, or a separate ParadeDB node via logical replication — which costs read-your-own-writes (§I.8).                                   |

**On query growth — we tested this, and it is confirmed.** A JSON term is encoded as
`path + type + value`, with the path **first**, so there is no "match this value under any path"
lookup. Every way of asking without naming a path returns nothing:

```sql
SELECT _id FROM e WHERE metadata @@@ 'guatemala';              -- 0 rows
SELECT _id FROM e WHERE metadata ||| 'guatemala';              -- 0 rows
SELECT _id FROM e WHERE _id @@@ 'metadata:guatemala';          -- 0 rows
SELECT _id FROM e WHERE _id @@@ 'metadata.*:guatemala';        -- parse error
SELECT _id FROM e WHERE _id @@@ 'metadata.country.value:guatemala';  -- 1 row ✓
```

Only the explicit path matches. The workaround is a disjunction naming **every** path:

```sql
WHERE _id @@@ 'metadata.country.value:guatemala OR metadata.country.label:guatemala
               OR metadata.author.label:guatemala OR metadata.summary.value:guatemala
               OR title:guatemala'
```

That is one index scan, not N queries — the plan stays a single `Custom Scan`. But **the query
string itself grows with every property in the tenant**, and it is generated per request.

⚠️ So the mapping explosion does not vanish; it moves from the index definition to the query text,
where nothing bounds it. We already build this list today (`documentQueryBuilder` fans a bare term
over `metadata.X.value` for every property), so the shape is not new — what is new is that the
4,500-field ceiling was the thing implicitly keeping that list short.

### What still has to be declared by hand

Removing the mapping does not make everything schema-free. A smaller schema comes back — the list of
properties we want to _sort_ by. Here is what that means on screen, if we index `metadata` as JSONB
and stop there:

| On screen                                          | What happens                                                                                                                                           |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Search box, and filtering by any property          | ✅ Works. No change.                                                                                                                                   |
| **Sort dropdown** — "sort by Date of ruling"       | ⚠️ Right rows, but the index does not help: Postgres sorts _every_ matching row to show you 30. Also silently wrong for numbers and dates unless cast. |
| **Counts next to filter checkboxes**               | ✅ Work — but only if the column is indexed as columnar. One cast, index-wide.                                                                         |
| **Editor ticks "Use as filter" on a new property** | ⚠️ Property doesn't become sortable until the index is rebuilt. Today it's instant.                                                                    |

Three terms in that table carry the whole of Part I, so in plain words:

**"Indexed as columnar"** — the index can keep two copies of a field. One answers _"which rows
contain this word?"_ (search). The other stores the actual values laid out column by column, which
is what _counting_ and _sorting_ need. Numbers get the second copy automatically; **text and JSON do
not, unless you ask.** Asking is a one-word change to the index definition and applies to the whole
`metadata` column at once — not per property. Forget it and facet counts do not fail gracefully,
they error.

**"Declared up front"** — the property is written **by name, in SQL**, into the statement that
creates the index, before anything is indexed. One line per property you want to sort by. Not in
that list, not fast to sort. Unlike the columnar switch above, this one _is_ per property.

**"Rebuild the index"** — re-reading every entity in the tenant and building the search index again
from scratch; hours on a large collection. You cannot append to the statement, you build a new index
and swap it. It runs online, so no downtime — but it is a full pass over the data.

⚠️ The sting is in the last two together: an editor ticks "Use as filter" in the UI, and someone has
to edit SQL and re-index the tenant before that property sorts properly. **A checkbox becomes a
deployment.**

> **Conclusion: a plain JSONB index gets us almost everything except _fast_ sorting.** Search,
> filtering and facet counts all work off the raw `metadata` column (measured — §I.3). Sorting works
> too, but without the index helping — Postgres sorts every matching row to give you one page —
> plus a silent lexicographic-ordering trap on numbers and dates. Buying the fast path back means naming each
> sortable property in the index. That is the one problem the next section has to solve.

## I.3 What shape do we store metadata in?

Uwazi stores each property as a **list of values** — an entity can have two authors, three
countries. Nothing in ParadeDB's documentation says how it handles that shape, and every previous
version of this evaluation guessed. **So we tested it**, against a real ParadeDB instance using our
actual metadata.

### What we found

| Question                                          | Answer                                                                                                                 |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Can we **search** metadata?                       | ✅ Yes, normally                                                                                                       |
| Can we **filter** by any property?                | ✅ Yes, including properties with several values                                                                       |
| Do the **counts next to filter checkboxes** work? | ✅ **Yes** — and correctly. An entity tagged both Guatemala and Honduras is counted under each.                        |
| Can we do all that **without a new table**?       | ✅ Yes. Directly off the metadata we already store.                                                                    |
| Can we **sort** by a property?                    | ⚠️ It returns the right order, but the index does not help — the database sorts every matching entity to show one page |
| Do **numbers and dates** sort correctly?          | ❌ Not by default. They sort like text: 100, 1000, 25, 9. Fixable, but it must be done deliberately per property type. |

### Why this matters

**What is left is one problem: sorting.** Not whether it works — it does — but whether it stays fast
as collections grow, and whether we can keep the sort dropdown up to date without an engineer
editing SQL every time an editor ticks a checkbox.

⚠️ Two honest caveats. First, this was tested on a handful of entities: it proves the behaviour is
**correct**, not that it is **fast** at our scale. Second, it was tested without our permission
rules switched on, and those could change the answer (§I.5) — which is why that is the next thing to
test.

### Three ways to solve the sorting problem

|                                    | What it is                                                                                                  | Verdict                                                                                                                                                                                                                                                                    |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. A separate values table**     | Copy every property value into a purpose-built table, one row per value. The design earlier drafts assumed. | **Weakened.** Its main justification — faceting — is gone. It also fixes the number-sorting trap for free, which is a genuine point in its favour. But it is the largest option by far, it slows down saving entities, and it is not certain it even makes sorting faster. |
| **B. A reshaped copy of metadata** | Keep one row per entity, but store a second, simplified version of its metadata alongside it.               | **Mostly pointless now.** It existed to avoid the value-list shape that turned out to work fine. It still would not solve sorting.                                                                                                                                         |
| **C. No new table**                | Use the metadata we already store, and name the sortable properties in the index.                           | **Front-runner.** Everything we confirmed works, works here directly, with no new data to build or keep in sync. Its weakness: each sortable property has to be named up front, and there is a hard limit on how many.                                                     |

### What decides it

One number, which nobody has looked up:

> **How many properties do our real tenants actually mark as filterable?**
>
> Around 40 → **Option C wins**, and the largest workstream in this migration disappears entirely.
> Around 400 → C is impossible, and we are back to Option A.

It is a single query against production data, and it is now the only thing standing between us and a
decision on the data model.

💡 One argument for Option A survives regardless of what we decide here: a values table would make
faceting and sorting faster **on Elasticsearch too**, and it would fix the number-sorting problem
permanently. That is a reason to consider it on its own merits — not a reason to assume it as part
of this migration.

## I.4 Tenancy — and why this is not a tool-only migration

This is the question with the most surprising answer, and earlier drafts got it backwards.

**Today:** one Elasticsearch index per tenant. Physical isolation. A tenant can be reindexed,
resized or repaired alone.

**Where the Postgres migration has already put us:** a single shared `entities` table with a
`tenant_id` column and row-level security
([005-add-entities-table.sql](../app/api/core/infrastructure/postgresql/schema_migrations/005-add-entities-table.sql)).
Logical isolation.

A ParadeDB index is an index **on a table**. So the default outcome of this migration is **one
multi-tenant search index** — the opposite of what we have now. That is not neutral:

- Index size is the sum of all tenants.
- One tenant's compaction and merge load lands on everyone (noisy neighbours).
- **Per-tenant reindex becomes impossible.** A rebuild rebuilds everything. Today, re-indexing one
  broken tenant is a routine operation.

Getting index-per-tenant back means partitioning:

```sql
CREATE TABLE entities (...) PARTITION BY LIST (tenant_id);
```

Postgres then creates an index per partition, which is structurally equivalent to today. But that is
**not a search decision** — it is a decision about the `entities` table that the v2 Postgres
migration has already made in the other direction. Costs: partition DDL on tenant creation, planning
time that grows past a few hundred partitions, and interactions with RLS and join pushdown that need
verifying.

⚠️ **So the honest answer to "is this a tool-only migration?" is no.** It either changes our search
tenancy model from physical to logical isolation, or it forces a change to the Postgres tenancy
model. Whichever we pick, someone outside the search module has to agree to it.

## I.5 The permission filter — the thing to check first

> **⚠️ Superseded — see `paradedb-findings.md`.** The prediction below is wrong in its mechanism and right about the conclusion, for a different reason. Measured: the permission predicate **does not** disqualify anything — Top-K stays at exactly 1.0 over-fetch and aggregates still push down, at every corpus size. But it is applied as a per-row heap filter, which makes it the **single largest cost in the whole evaluation**: 7.5× on latency versus no check, and ~30× on throughput under concurrent load. Being an admin does not help — the `bypass_rls` branch costs almost the same.

Our Postgres read policy
([010-add-permission-rls-infrastructure.sql](../app/api/core/infrastructure/postgresql/schema_migrations/010-add-permission-rls-infrastructure.sql)):

```sql
"tenant_id" = current_tenant() AND (
     current_setting('uwazi.bypass_rls') = 'true'   -- admin / editor / system
  OR "published" = true
  OR "_perm_read_refs" && string_to_array(current_setting('uwazi.ref_ids'), ',')
)
```

This is genuinely better than what we do today — the same rules currently live in the query builder
and every call site has to remember to apply them. Under RLS the database refuses to return rows the
actor cannot see, regardless of what the query says. For a product used by human-rights
organisations, that is a materially stronger statement.

**But that predicate is a three-way disjunction containing a GIN array-overlap operator, and it is
very unlikely to push down into a ParadeDB index scan.** If it doesn't:

- **Top-K sorting** over-fetches and filters afterwards, instead of stopping at K.
- **Aggregate pushdown falls back** to ordinary Postgres execution — so facets get slow.

That would degrade search, sort _and_ facets simultaneously, for every non-admin user — while
looking perfectly fine in any benchmark run as an admin, because admins take the `bypass_rls`
branch.

⚠️ **One `EXPLAIN ANALYZE`, run as a collaborator, answers this**, and I would run it before
anything else. It gates every performance question in Part II, and it is currently a footnote in the
existing material.

## I.6 Full text — two shapes that have to change

> **⚠️ Superseded — see `paradedb-findings.md`.** Full text has now been built and measured. The per-page shape below is correct and was adopted. The three per-language options in the table are **not** — "partial indexes keyed on `language`" is impossible, because a relation may only have one ParadeDB index, and the aliased-tokenizer option silently breaks snippets (`pdb.snippet` returns NULL for any match from an aliased field). The answer is to **partition the table by language**, one partition per supported stemmer plus a DEFAULT, which gives per-language stemming and snippets with no duplication.

Neither of these is optional, and neither is controversial. They are just work.

**Per-page rows instead of `[[12]]` markers.** ParadeDB has no character filters. Fed to any
tokenizer, our page markers would index a page-number token between every pair of words — inflating
the index and shifting term positions, which breaks phrase and proximity search on document text.
The fix is to store full text one row per page, making the page number a column:

```sql
CREATE TABLE entity_fulltext (
  tenant_id TEXT, entity_id TEXT, file_id TEXT,
  page      INTEGER,
  language  TEXT,
  contents  TEXT,
  PRIMARY KEY (tenant_id, file_id, page)
);
```

This is a better design than what we have — it also removes a scheme that inflates stored text by
the length of a marker per word — but it touches PDF processing, the index path and snippet
assembly.

**Per-language analysis has no free equivalent.** Today ES picks the analyzer from the field name,
so `fullText_persian` and `fullText_thai` each get correct stemming and stopwords from one index
definition. ParadeDB fixes the tokenizer **per indexed field**, not per document. Three options,
each with a real cost:

| Approach                                  | Cost                                                             |
| ----------------------------------------- | ---------------------------------------------------------------- |
| One aliased tokenizer per language family | Index size grows with the number of families                     |
| Partial indexes keyed on `language`       | More index objects to manage; needs partitioning-like discipline |
| ICU tokenization for everything           | Simplest; weaker stemming for stemmed languages                  |

⚠️ For a multilingual human-rights archive, "weaker stemming in Spanish and Arabic" is a real
quality regression, not a footnote. **With the metadata shape now largely settled by measurement
(§I.3), this is arguably the largest genuinely open design question left**,
and only our corpus can settle it.

## I.7 The write path

Today, indexing happens **after** the commit, out of band. If ES is slow, the write still succeeds.

Under ParadeDB, the index is maintained inside the transaction. One entity save becomes: write the
row → update its index → (under Option A) write N value rows → update their index. All
synchronous.

⚠️ What to load-test is **bulk imports, reindexing and the migration itself** — not search. A single
entity save gaining a few milliseconds is fine. A 200,000-entity import is where this shows up.

💡 There is a topology that removes this entirely — see §I.8.

## I.8 Scaling, replicas and licensing

We run one read/write primary plus two read replicas. Here is what each option does with them.

|                      | Community (AGPL-3.0) | Enterprise (paid) |
| -------------------- | -------------------- | ----------------- |
| Maximum cluster size | **1**                | Unlimited         |
| Read replica support | **❌**               | ✅                |
| High availability    | **❌**               | ✅                |
| Logical replication  | ✅                   | ✅                |

> _"In a primary-replica topology, ParadeDB indexes in ParadeDB Community are only available on the
> primary, as the Community edition does not support physical replication."_

**On Community, our two read replicas contribute nothing to search.** Physical replication carries
the heap and the B-trees; the ParadeDB index is primary-only. So all search traffic lands on the
write primary — which is now also doing index maintenance inside every write transaction (§I.7).
That is the worst possible combination of the two.

**On Enterprise**, replicas share the primary's index through physical replication (they don't build
their own). It requires `hot_standby_feedback=on` and a named replication slot, or replicas suffer
frequent query cancellations.

**The Community-legal workaround, and its real price.** Logical replication is available in both
editions, so you can run a _separate_ ParadeDB instance as a logical subscriber that builds its own
index. That gives a dedicated search node and keeps the primary free of index maintenance. But be
clear about what it costs:

⚠️ **It cancels two of the five things we said we were gaining.** Read-your-own-writes goes (back to
eventual consistency), and "no separate cluster to operate" goes (you are operating a second
database again). DDL is not replicated either, so schema changes must be applied by hand on the
subscriber.

**Licensing.** Community is AGPL-3.0; Enterprise waives the copyleft provision. ParadeDB offers
complimentary Enterprise to non-profits case by case, which likely covers HURIDOCS. The harder
question is **downstream**: Uwazi ships MIT and is self-hosted by other organisations, who get
clustering and replication from Elasticsearch for free today. This warrants a real legal opinion,
not ours.

**Ceiling.** ParadeDB documents single-node vertical scaling, describes 1–10 TB as comfortable, and
cites 10 TB as the largest production database they have seen; Citus for sharding beyond that. We
should put our actual corpus size next to that number.

# Part II — Searching

Everything here is downstream of Part I. Each section names what it depends on.

## II.1 The search box

**What the user sees:** a search field, searching as you type (350 ms debounce), with a "Search
Tips" modal beside it.

The risk is not in the box — it is in the modal. We publish a **syntax contract** to users in
translated help text ([SearchTipsContent.tsx](../app/react/App/SearchTipsContent.tsx)):

| Operator         | We tell users                | Under ParadeDB                                              |
| ---------------- | ---------------------------- | ----------------------------------------------------------- |
| `"Costa Rica"`   | exact phrase                 | ✅ supported                                                |
| `AND` `OR` `NOT` | boolean search               | ✅ supported                                                |
| `"the status"~5` | words within N of each other | ⚠️ phrase slop exists; exact syntax needs confirming        |
| `juris*`         | wildcard                     | ⚠️ **not part of the query parser** — a separate query type |
| `198?`           | single-char wildcard         | ⚠️ same problem, no obvious shorthand                       |

**Three of the five operators we actively teach are unconfirmed.** For a legal and human-rights
archive, `juris*` is not a power-user curiosity — it is how researchers work around inflection and
transliteration.

Either we pre-parse the query ourselves (pull the `*` and `?` clauses out and rewrite them as a
regex query before handing the rest to the parser), or we change what we tell users. The first is
real work; the second is a visible product regression.

💡 One thing that ports cleanly: today we ask Elasticsearch whether the user's string is valid
Lucene and silently downgrade to a simpler parser if not, so `status AND (` returns results rather
than an error. ParadeDB's parser has a lenient mode that preserves that "never show an error"
property. The _results_ for a half-typed query may differ, though — and since we search as you type,
every intermediate keystroke is a real query.

## II.2 The filters sidebar

**↩︎ Depends on §I.3 (the data shape), §I.5 (RLS pushdown).**

This is roughly half the migration. Re-read the self-excluding facet contract in Part 0 if it didn't
stick — everything here rests on it.

Beyond the counts themselves, the sidebar has a UI contract nobody documents:

- Each option shows its count, and options are sorted by count.
- **Options with zero results are hidden entirely** — unless already checked.
- Below the list, an "N more options" expander, and past a threshold, "N+ more options — Narrow your
  search."
- A synthetic **Any** option, and a **No label** bucket for missing values, both assembled in
  post-processing rather than by the search engine.
- An **AND / OR toggle** on multi-selects, which becomes `GROUP BY … HAVING count(DISTINCT …) = n`.

### This got a lot better than the earlier drafts said

Earlier drafts called facets the single biggest unknown in the migration, on two claims that have
since fallen over.

**Claim 1: "faceting over raw metadata is impossible, so we need a normalized table." Wrong —
measured.** §I.3 shows facet counts working correctly straight off the metadata we already store,
including for properties with several values. No join, no projection table. The one requirement is
that the column be indexed as columnar (§I.2).

**Claim 2: "ParadeDB's aggregates are not pushed down across joins."** Too strong, and the current
documentation contradicts it:

- **Standard SQL aggregates _are_ pushed down across joins** — `COUNT`, `COUNT(DISTINCT …)`,
  `GROUP BY` on columns from any table in the join (including JSON sub-fields via `->>'key'`),
  per-aggregate `FILTER (WHERE …)`, and `HAVING`. Conditions: every table has a ParadeDB index, an
  equality join condition, indexed join and group columns, no window functions.
- It is specifically the `pdb.agg()` **function** that is single-table only.
- There is also a **filters aggregation** — `pdb.agg(…) FILTER (WHERE <search query>)` — designed to
  compute several differently-filtered aggregates in one query. That is aimed squarely at our
  self-exclusion pattern.

⚠️ **What is left of the risk.** Not "N queries are unavoidable" — that was wrong twice over. What
remains is narrower and entirely about scale:

1. **Latency at real volume.** §I.3 proved the behaviour is correct on a handful of entities. It
   says nothing about what a 20-facet sidebar costs over a few million.
2. **Whether RLS disqualifies the pushdown** (§I.5). If the permission predicate cannot enter the
   scan, these aggregates fall back to ordinary Postgres execution for every non-admin user.

The second is the one to test first, because it can undo the good news from §I.3 entirely.

💡 **Worth checking regardless of the decision.** Every facet today runs in `global` scope with
`size: 2000`, once per filterable property, across the **entire tenant** rather than the result set.
If a large share of current library slowness is that shape rather than Elasticsearch, the same shape
will be slow on ParadeDB too — and it is fixable on ES today for a fraction of the cost.

## II.3 The sort dropdown

**↩︎ Depends on §I.3.**

The dropdown lists Title, Date added, Date modified, **plus every text, date, numeric and select
property with "Use as filter" ticked** ([sortComponets.ts](../app/react/Library/helpers/sortComponets.ts)) —
a user-controlled, unbounded set.

**This is now the only unsolved problem in Part I.** §I.3 measured everything else working off the
raw JSONB column — search, filtering, facet counts. Sorting is the one thing that does not.

To be precise about what "does not" means: sorting **works and returns the right rows**. It just
does not use the index — Postgres materialises every matching row and sorts it, rather than the
index stopping at the first K. On a library query over a large collection that is the difference
between a Top-K scan and a full sort of the result set. Only a declared alias per property gets the
fast path.

⚠️ Underneath that sits a **correctness** trap: numeric and date properties sort lexicographically
unless explicitly cast (`100, 1000, 25, 9`). Silent, no error. See §I.3.

So each entry in this dropdown needs a line of SQL in the index definition, and adding one means an
online rebuild. Today it is an instant mapping update. **This single feature is what the entire data
shape decision in §I.3 is now about.**

⚠️ And note the caveat that cuts the other way: a values table makes sorting by any property
_possible_, but sorting by a **joined** table's column is not the Top-K shape either, so it may not
be fast. Neither option has been measured at scale. Do not assume either is faster than what we
have today.

**Alphabetical sorting and accents.** Title sorting uses lowercase + accent folding, or ICU
collation when `USE_ELASTIC_ICU=true` (which is why there is a custom Docker image in the repo).
Postgres has native ICU collations, so this ports — but it is a **per-locale visible ordering**, so
it needs verifying per language. A Spanish or Arabic user noticing that "ñ" sorted differently is a
real support ticket.

> **⚠️ Superseded — see `paradedb-findings.md`.** "So this ports" is wrong, and this turned out to be one of the sharpest findings. ParadeDB will only take the fast Top-K path on text under `COLLATE "C"` — raw byte order, which puts all uppercase before any lowercase and "ñ" after "z". Under the database's normal collation it refuses. So the choice is **indexed text sorting or locale-correct alphabetical ordering, not both**, and it applies to every text property in the sort dropdown including Title, the default sort. Declaring the property in the index does not help for text.

## II.4 Nested properties

**↩︎ Depends on §I.3 — and this dependency got _worse_, not better.**

The nested-property filter lets you require values across sub-fields — and in **strict** mode,
require them to match _within the same row_ of the nested table rather than anywhere in the
property. That distinction is the entire point of the feature.

It depends on Elasticsearch **nested documents**, which have no ParadeDB equivalent. The
reconstruction everyone assumed is an `ordinal` column: same array element means same ordinal.
Semantically sound, and a full reimplementation of one of the fiddliest code paths we have.

⚠️ **But `ordinal` only exists if we build a values table.** §I.3's results point at Option C —
no new table — and Option C has nowhere to put an ordinal. That leaves an open question the
experiment did not cover: **does Tantivy preserve array position within a JSON path, such that
strict-nested semantics can be expressed against raw `metadata` at all?**

If it does not, then either nested-strict needs its own small side table, or it becomes the one
feature that forces the larger projection. Worth adding to the same test session that answers §I.5.

> **⚠️ Superseded — see `paradedb-findings.md`.** Answered: Tantivy does **not** preserve array position — a strict query silently returns the **non-strict** result set (533 rows where the correct answer was 266), with no error. But it does **not** force a projection table. Using the index to narrow to candidates and re-checking the pairing in SQL over just those candidates returns the correct answer and stays affordable.

The UI does not change. The semantics have to be preserved exactly, or a filter that used to mean
"this person, in this role" starts meaning "this person somewhere, and this role somewhere" — with
no visible error. The good news: `search.spec.js` has dedicated test blocks for strict-nested and
second-level nested behaviour.

## II.5 Searching inside a document

**↩︎ Depends on §I.6.**

Open an entity, search within it, get snippets grouped under **"Page 12"** headers; click one and
the PDF jumps to that page.

That whole chain depends on the `[[12]]` marker hack from Part 0, which cannot survive without
character filters. With the per-page table from §I.6 the page number becomes a column and snippets
come from the matching row.

**Nothing in the UI changes.** The feature is preserved exactly; the data model underneath moves.
🔁 It will probably get _faster_ — today this runs with `number_of_fragments: 9999` over one entity.

## II.6 Typeahead — probably a win

**Entity pickers and relationship fields** use search-as-you-type with 2- and 3-gram subfields, plus
a separate ngram field that catches matches in the _middle_ of a word; the V2 lookup sends a fuzzy
query tolerating two typos. Edge-ngram tokenizers and ParadeDB's fuzzy matching (also max edit
distance 2) cover both. ✅

**Typeahead inside a filter** ("Narrow your search") currently runs the _entire library query_ with
`limit: 0`, keeps one aggregation, and appends a wildcard filter on the label — so every keystroke
costs a full faceted search. A terms aggregation on the columnar `metadata` column (§I.3), or an
`ILIKE` on the label, is a cleaner implementation and likely **faster than today**. Worth calling
out as a probable win.

⚠️ One caveat: ParadeDB does not support highlighting on fuzzy matches. We don't highlight in the
picker today, so it doesn't bite — but it forecloses "show me why this matched" in any fuzzy context
later.

## II.7 Permissions and the "Shared with" facet

**↩︎ Depends on §I.5.**

Behaviour is identical and correctness improves (§I.5) — with one exception. The **"Shared with"**
facet, which counts entities per user and group, is built today with a nested + `reverse_nested`
aggregation. With no nested documents, it becomes `COUNT(DISTINCT entity_id)` over a join. Fine
semantically; falls under the §II.2 pushdown question.

## II.8 What does _not_ change

Reassuring, and worth stating plainly:

- **The HTTP API.** The request schema already uses our vocabulary, not Elasticsearch's, and
  responses are already post-processed into our own bucket shape before reaching the frontend. What
  gets rewritten is the translation layer between them — roughly 1,240 LOC across two query builders
  and the aggregation builder. It exists today as _our params → ES queries_; it becomes _our params
  → SQL_.
- **The frontend.** No changes, except the Search Tips modal if wildcards don't survive (§II.1).
- **The map view.** We run **no geographic queries at all** — the map filters on "does this entity
  have a geolocation property" and projects coordinates for the browser to plot. ParadeDB's own
  comparison table flags geospatial as a gap needing PostGIS; that gap does not apply to us.
- **Pagination.** Offset-based everywhere. ParadeDB drops `scroll` and `search_after`; we use
  neither.
- **CSV export.** Re-runs the library query and streams. Inherits whatever the library query does.

# Part III — Where we actually are

## What we would gain

- **Read-your-own-writes.** Save an entity, search for it, find it. The "I saved it but it's not in
  the library yet" class of bug disappears. _(Unless we adopt the logical-replication topology —
  §I.8.)_
- **No more index drift.** The class of bug where Postgres and Elasticsearch disagree stops
  existing.
- **No cluster to operate.** One database to back up, secure, upgrade and monitor. _(Same caveat as
  above.)_
- **Permission rules enforced by the database** rather than remembered by every call site.
- **No mapping migrations.** Adding a property stops being a schema event — for matching and
  filtering, at least.
- **Semantic search becomes reachable** — BM25 and vector retrieval in one index. Not a reason to
  migrate, but a door that opens.

## The prototype, once the cheap questions are answered

Build the chosen shape against a copy of our largest real tenant and rebuild exactly one screen: the
library, with its default filter sidebar, a text search and a sort. Measure p50/p95 against the same
interaction on the current cluster, **as a collaborator, not as an admin** (§I.5).

## The one thing worth saying to anyone short on time

The mapping ceiling is real and ParadeDB removes it. What it asks in exchange is narrower than we
thought a week ago: **search, filtering and facet counts all work directly off the metadata we
already store** — that is measured, not assumed (§I.3). The one thing it will not do is **sort by a
property** without naming that property in the index definition up front.

So the trade is: an unlimited number of properties, in exchange for a limited number of _sortable_
ones. Whether that is a good deal depends on one number nobody has looked up — how many properties
our real tenants actually mark as filterable.

**That query, and the RLS `EXPLAIN` (§I.5), are worth more right now than any amount of further
design.** And before either: check whether Elasticsearch's `flattened` type solves the original
problem without a migration at all (§I.2).
